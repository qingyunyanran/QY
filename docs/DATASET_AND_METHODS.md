## 1. 数据集是怎么产生的

数据集里只有 `(obs, act)` 对，没有 reward、没有 next_obs、没有 done。因为数据是"专家策略逐步执行、只记录动作"得到的——专家只输出"该走哪一步"，不输出 reward。

**这里必须纠正一个容易搞错的点**：8 任务这套数据（`sd_8task_1k.npz`）的老师**不是运动规划 solver**，而是 `c8v5_cons`——PPO 训出来的 8-head CL 模型（终评 92.0%）。`_sd_collect.py` 开头写得很明确：

```
Collect expert (obs, action) pairs from the 8-task multi-head CL policy.
The multi-head expert is only a data source here -- nothing of its head
structure survives into the student.
```

solver 只在第 2 节那个"单任务基线 91.7%"里直接出场，不参与这套 BC 数据的生成。

### 1.0 三个词先分清（容易混）

| 说法 | 指什么 | 产出 | 成本性质 |
|---|---|---|---|
| **专家策略**（solver 或 PPO 模型） | 一个能完成任务的策略：规则程序或已训好的网络 | **代码 / `.pt` 权重** | 一次性投入，**可能失败** |
| **采数据** | 跑这个策略，逐步记录 `(obs, act)` | **npz 数据集** | 机械性，专家通了就一定能采到 |
| **训学生** | 用 npz 训神经网络 | `.pt` 权重 | 要 DAgger 反复迭代 |

本文说的"专家"一律指**第一行的策略**，不是数据集。数据集是第二行"采数据"的产物。

这个区分重要在于两者的风险完全不同：

- 官方已有求解器的任务（8 个稠密任务、PlaceSphere）→ 第一步成本为 **0**
- 没有官方求解器的任务（RollBall）→ 全部风险都压在第一步，且这一步**不保证能做成**

**还有一条推论要记住**：学生能到多高，受老师上限约束。老师是 92.0% 的模型，学生做到 92.4%，说明已经贴着天花板——再往上必须换更强的老师，不是加数据或者加容量能解决的。

### 1.1 生成流程

```
专家策略（c8v5_cons，8-head）→ 在环境里逐步执行
   → 每步记录 (obs_t, act_t) → 只保留成功 episode → npz
```

- `obs`：`unified_obs.py` 统一编码，8 个任务均为 **48 维**
- `act`：8 维 `pd_joint_delta_pos`，`ACTION_LIMIT=1.0`
- `ep`：episode 编号（用于 3 帧堆叠和 episode 分组）
- `tid`：任务编号（**只在训练时用于均衡采样，推理时不用**）
- 只保留成功 episode：`_sd_collect.py` 的注释写明"BC 学生学到失败轨迹就会继承失败"（`SD_KEEP_FAIL=1` 可关掉）


### 1.2 实际数据量

初始数据集 `demos/sd_8task_1k.npz`：

| 任务 | 轨迹数 | 帧数 | 平均步长 |
|---|---|---|---|
| PegInsertionSide | 910 | 36,280 | 40 |
| StackCube | 865 | 16,520 | 19 |
| PullCube | 999 | 17,542 | 18 |
| PickCube | 936 | 20,919 | 22 |

加 5 轮 DAgger 后累计 **22,625 条轨迹 / 约 73 万帧**。

### 1.3 为什么只有专家数据

这是**设计选择**，不是能力限制：专家生成数据只要一次规划，而 RL 从零探索在这批任务上实测只有 0–7%（见第 5 节）。代价是数据天然缺 reward，因此只适合模仿学习类算法——这一点在文档末尾的「局限」里明确写了。

## 3. 部分二：单头多任务联合训练（92.4%）—— 严格单模型的上界

**先明确一件事，避免误读**：这一部分是**联合训练（joint / multi-task）**，不是持续学习。所有 8 个任务的数据一次性加载（`_sd_train.py` 里 `SD_DATA` 指向合并后的 npz），按任务均衡采样，训 200 epochs。

它**不是 Class-IL**——任务没有按顺序到达，也没有"训完就不能回头"的约束。它证明的是："一个 head 有能力服务 8 个任务"，这是做 Class-IL 的**必要条件**，但不是 Class-IL 本身。

它的定位是**上界参照**：如果允许数据全部同时可用，单头能到 92.4%。真正的顺序学习见第 4 节。

### 3.0 "训学生"到底是什么

**学生 = 一个模仿专家的神经网络。** 它不需要理解任务，只需要看着专家的数据学会"看到这个观测，该出这个动作"。

为什么必须有学生，不能直接用专家？因为规划器**不可部署、也不可持续学习**：

| | 专家（求解器） | 学生（网络） |
|---|---|---|
| 形态 | 规划程序（mplib + IK + 碰撞检测） | MLP 256-256 |
| 输入 | 完整场景几何、精确物体位姿 | 48 维观测向量 |
| 单步耗时 | 每步重新规划，几十~几百 ms | 一次前向，微秒级 |
| 能否被训练 | ❌ 无参数可学 | ✅ 可以顺序更新 |
| 能否做 CL 实验 | ❌ 规划器不是可训练对象 | ✅ 这是唯一的载体 |

第二列最后一行是关键：**持续学习要求"参数被顺序更新"，规划器没有参数，所以 CL 实验只能做在学生身上。** 整条链路是：

```
solver（规则，不可部署）
   → 采数据（(obs,act) 对）
      → 训学生（网络，可部署、可顺序学习）
         → 在学生的参数上做 CL
```

所以"训学生"这一步是把"规则"翻译成"可训练参数"的桥。没有它，后面所有 CL 实验都没有载体。

本文出现两种"学生"，老师不同：

| 学生的位置 | 老师（标签来源） | 训练方式 | 结果 |
|---|---|---|---|
| 部分二（§3） | **`c8v5_cons`（8-head PPO CL 模型，92.0%）** | 监督回归 BC + DAgger | 65.5 → **92.4%** |
| 部分三（§4）的 head | **PPO 单任务专家**（`peg75m` 等） | 蒸馏（anchor / MTD） | 88.7–92.0% |

注意两行的老师不同：部分二的老师是"已经会 8 个任务的多头模型"，部分三的老师是"每个任务单独训的单任务专家"。

### 3.1 方法

单个 MLP 策略头，**全程一个模型、一个 head、不用任务标签**。训练是纯监督回归，不是 RL。

代码：`_sd_train.py`（训练）、`_sd_collect.py`（采初始数据）、`_sd_dagger.py`（DAgger 采集）

```
输入：obs 3 帧堆叠 (N, 48×3=144)  →  MLP(256-256)  →  输出 8 维
loss = 高斯 NLL（SD_NLL=1 默认）或 MSE / L1
优化器 Adam，LR 3e-4，200 epochs，batch 2048
```

两处容易记错的细节：

- **学生吃 3 帧堆叠（144 维），老师只吃单帧（48 维）**。老师是 `Agent(UNIFIED_OBS_DIM)`，学生是 `Agent(UNIFIED_OBS_DIM * STACK)`，`STACK=3`。堆叠是为了让单头能推断运动趋势，弥补没有任务标签的信息缺失。
- **Peg 有私有 base**（`PRIVATE = ("PegInsertionSide-v1",)`），因为它的观测分布和其他 7 个差得最远。


**关键设计：按任务均衡采样。** 每个 batch 里 8 个任务贡献相同数量的样本（`per_batch = BS // n_tasks`），否则 PokeCube（28 步）和 PullCube（18 步）会被 PullCubeTool（34 步）压制。

评测走 `actor_mean` 确定性前向（不采样动作），N=100。

### 3.2 只用 BC 的结果：65.5%

7,425 条专家轨迹直接做 BC，单头只到 **65.5%**。原因不是数据少，是**8 个任务共享一个 head 时状态分布冲突**：同一个观测在两任务下该输出不同动作。

### 3.3 DAgger 把 65.5% 拉到 92.4%

#### 它解决什么问题

纯 BC 有个致命缺陷，叫**复合误差（compounding error）**：

```
学生第 1 步偏了 1 cm  →  进入一个专家从不经过的状态
   →  这个状态没在训练集里  →  学生输出更离谱的动作
      →  偏 5 cm  →  偏 20 cm  →  失败
```

学生没见过"偏了之后该怎么办"，因为它只学过"专家在正确位置上怎么走"。偏差一旦出现就无法自愈。

#### DAgger 怎么修

**DAgger = Dataset Aggregation**（Ross et al., 2011）。它只改一件事：**数据从谁的分布来。**

| | BC | DAgger |
|---|---|---|
| 谁在环境里走 | **专家** | **学生** |
| 记录哪些状态 | 专家会经过的状态 | **学生会经过的状态（包括走偏、恢复、失败）** |
| 标签从哪来 | 专家 | 专家（在同一状态上标注） |

四步循环（我们的实现，`_sd_dagger.py`）：

```
1. 学生驱动环境，跑 N 个 episode，记录每一步的观测
2. 老师（c8v5_cons 8-head）在这些观测上给出动作标签
3. 把这批 (obs, 老师动作) 追加到历史数据集
4. 用聚合后的全部数据重训学生
```

关键三处实现细节：

- **学生驱动**：环境里的动作是学生输出的，所以状态分布是学生的。这是 DAgger 与 BC 唯一的本质区别。
- **老师在同一状态上给标签**，不需要从头重新规划一条完整轨迹。老师是网络，任意状态随时能问，一次前向即可。
- **保留所有访问到的状态，不只成功的**。`_sd_dagger.py` 注释写得直白：*"a state where the student is already off-track is precisely the state that needs a label"*——走偏的状态恰恰是最该标注的状态。

另外两个格式差异（容易忽略）：

- 老师吃**单帧 48 维**，学生吃**3 帧堆叠 144 维**，标签按环境相同方式 clip
- 老师是 8-head，`tid` 决定用哪个 head；学生只有 1 个 head，`tid` 永远不进网络

#### 为什么只加 200 条就够

因为新增的不是"专家本来就会的状态"，而是"学生走偏了、专家从不经过的状态"。这 200 条覆盖的正是 BC 的盲区，性价比极高——帧数只涨 41%，成功率涨 12.9 个点。

**注意轨迹会变长**：DAgger 后平均步长从 18 涨到 56（PullCubeTool 34→47）。因为记录的是学生完整的一趟（含走偏和绕回来），不是专家的最优路径。所以按帧数算成本会低估。

#### 为什么停在 92.4% 上不去了

老师的上限是 **92.0%**（c8v5_cons 的终评）。学生做到 92.4%，已经和老师打平——**DAgger 收敛之后，学生的天花板就是老师的天花板**。

这也解释了后面扩到 10 任务为什么 Pyramid/Plug 是 0%：老师自己在这两个任务上就弱，学生无从学起。再往上必须换更强的老师，加数据、加容量都没用。

| 轮次 | 每轮新增（条/任务） | 累计轨迹 | 成功率 |
|---|---|---|---|
| 初始 BC | 831–1000 | 7,425 | 65.5 |
| DAgger r1 | 200 | 9,025 | 78.4 |
| DAgger r2 | 400 | 12,225 | 83.4 |
| DAgger r3 | 400 | 15,425 | 86.4 |
| DAgger r4 | 400 | 18,625 | **91.1** |
| DAgger r5 | 500 | 22,625 | **92.4** |

**为什么这招有效**：只加 200 条/任务（帧数涨 41%）就涨了 12.9 个点。新增的不是"专家本来就会的状态"，而是"学生走偏了、专家从不经过的状态"。这些帧正是纠正信号。

**注意轨迹会变长**：DAgger 后平均步长从 18 涨到 56（PullCubeTool 34→47）。因为专家要把走偏的学生"绕回来"，绕路的部分也是监督数据。所以按帧数算成本会低估。

### 3.5 扩到 10 任务的教训

同一个单头继续加 Pyramid 和 Plug：

| | 8 任务 | 10 任务 |
|---|---|---|
| 8 个稠密任务均值 | 92.4 | 92.6 |
| PyramidStack | — | **0** |
| PlugCharger | — | **0** |
| 10 任务均值 | — | **74.1** |

Pyramid 和 Plug 是 `reward_mode=none`（稀疏奖励），专家轨迹本身能到 87%/89%，但单头学不会——这两个任务的动作模式（堆叠、插孔）与前 8 个差异过大，一个 head 的容量吃不下。**所以这两个任务已按导师要求剔除**，任务集回到 8 个稠密任务。

### 3.6 既然 92.4% 已经很好，为什么还要做 CL 实验

**不是因为观测维度不一样。** 维度差异（Pyramid 68 / Plug 66 / PlaceSphere 56 / 其余 48）是用 `unified_obs.py` 的补齐机制消掉的：`TGT = 48 + UO_EXTRA_N`，所有任务都补齐到同一宽度，输入层不需要改。这是工程细节，不是"需要重做 CL"的原因。

**真正的原因：92.4% 这个数字是"作弊"来的。** 它成立依赖三个现实中往往不成立的前提：

| 前提 | 联合训练（§3） | 持续学习（§4） |
|---|---|---|
| 所有任务的数据**同时可用** | ✅ 一次性加载 73 万帧 | ❌ 任务逐个到达，旧数据可能不允许留存 |
| 老师**一直留着** | ✅ c8v5_cons 随时待命 | ❌ 8 个老师 = 8 份 ckpt，且要先训出来 |
| **参数量固定** | ✅ 单 head | ✅ 必须固定，否则就成了每任务加一个网络 |

第 3 条是"严格单模型"设定的核心约束：**不能每来一个任务就长一个新网络**，否则参数量随任务数线性增长，那就不叫一个模型了。所以 Progressive Networks 那类做法被排除了。

于是 CL 实验要回答的问题不是"能不能一次训到 92.4%"，而是：

> **在"只能看到当前任务、不能回头重训旧任务、参数量固定"这三个约束下，还能保住多少？**

这两条线的关系是**上界与可行解**：

```
联合训练（数据全在手）      92.4%   ← 上界
   ↓ 加上"任务顺序到达"约束
CL：冻结主干 + adapter      88.7%   ← 可行解（c8v2_ad）
CL：无任何保护（naive）      76.6%   ← 下界（c8v7）
```

**注意 88.7% 的取得方式**：不是靠 ER/MTD 的正则，而是靠**冻结主干**——旧任务的 base 和 head 一个字节都没动，遗忘在构造上就不可能发生。这也是为什么 ER/MTD 相对 naive 没有正贡献（p≈0.49）：想保护的东西本来就没坏，正则没有发挥空间。

**所以 CL 实验的真正产出是一个负结果**：在这批任务上，稠密奖励 + 参数量固定 + 版本兼容的观测下，**冻结主干就足以保住旧任务，蒸馏正则不是必需的**。这个结论比"MTD 有效"更可信，因为它有 3 seed 配对支撑。

## 4. 部分三：CL 主实验 —— PPO + ER + MTD

这一部分是你问的"MTD 是啥"，从基础讲起。

### 4.1 先看整体：这是持续强化学习，不是模仿学习

代码：`ppo_er_unified.py`（1,874 行），启动脚本 `c8v2_ad.sh` / `c8v4_picktrunk.sh` / `c8v5_cons.sh` / `c8v7_naive.sh`。

它**从环境拿 reward**（`normalized_dense`，8 个任务全部可用），做 PPO 在线训练。跟 npz 数据集无关。

**任务按顺序到达**：

```
Peg → Stack → Pull → Pick → LiftPeg → Push → Poke → Tool
```

训完任务 t 才能看到任务 t+1，且**不允许回头重训旧任务**——这是持续学习的核心约束。

### 4.2 这一部分的实际结构（必须说清楚）

`--multi-head` 打开后，`n_heads = len(task_seq)`，即**每个任务一个 head**：

```
                    ┌── head_0 (Peg)      ┐
                    ├── head_1 (Stack)    │
obs(48) → shared base(256-256) ──┼── head_2 (Pull)     ├── 8 维动作（按 task_idx 选 head）
                    ├── ...              │
                    └── head_7 (Tool)     ┘
```

另外 Peg 有**私有 base**（`--private-base PegInsertionSide-v1`），因为它的观测分布和其他 7 个差异最大。

**所以这一部分是 multi-head + per-task adapter，不是单模型。** 你不能拿它跟部分二（92.4%）比"谁更强"，两者设定不同。我在文档里单独标注，避免混淆。

### 4.3 MTD 是什么

#### 一句话

> **MTD = Multi-Teacher Distillation，多教师蒸馏。对回放缓冲里的每一条旧样本，按它来自哪个任务，去找那个任务自己的专家策略，用专家的输出当标签做 MSE 蒸馏。**

#### 为什么需要它

先看问题。在一个序列里，任务 7（Tool）正在训练时，任务 0（Peg）的专家策略**已经不在显存里了**——它在训完 Peg 之后就被丢掉了（或者只保留在当前任务的 anchor 槽位）。于是老任务的 head 没有任何东西约束它，只有 replay buffer 里的旧动作可做 BC。

但 BC 旧动作是个很弱的约束：

- 旧动作是**采样**出来的（有噪声），不是最优动作
- 对动作做 MSE 会同时把噪声也学进去
- 代码注释里记了实测：`StackCube 87% → 25% over a 5-task ER run`（只靠 ER 的 BC 项，5 个任务后 Stack 从 87 掉到 25）

所以要一个**更强、更干净的旧任务监督**——这就是教师。

#### 三个蒸馏项的层次关系

代码里有三个不同的蒸馏项，容易混，这里分清：

| 名称 | 参数 | 作用对象 | 教师来源 | 权重 |
|---|---|---|---|---|
| **anchor term** | `--anchor-coef` | 当前任务的 rollout 观测 | 当前任务专家 | 2.0 |
| **ER / BC term** | `--bc-coef` | replay 里的旧**动作** | 无（用存下来的 act） | 0.05 |
| **MTD** | `--mtd-coef` | replay 里的旧**观测** | **该样本所属任务的专家** | 2.0 |

区别一句话：

- anchor：**当前任务** vs **当前任务的专家**
- ER/BC：**旧任务** vs **旧动作（离线存的）**
- MTD：**旧任务** vs **旧任务的专家（活的策略）**

MTD 比 ER/BC 强的地方就在教师是"活的策略"而不是"冻结的旧动作"：专家在任何观测上都能给出正确动作，而旧动作只在它被采到的那一个状态上有效。

#### 数学形式

设 replay 采出一个小批 `B`，每条样本带任务号 `tid_i`。按 tid 分组，对每组 `g`：

```
L_MTD = Σ_g  (n_g / |B|) · MSE( π_θ(obs_i; head_g) ,  π^{E}_{g}(obs_i) )
```

其中 `π^{E}_{g}` 是任务 g 的冻结专家，`n_g` 是组内样本数。最后加到总 loss：

```
L = L_PPO + 0.05 · L_BC + 2.0 · L_anchor + 2.0 · L_MTD
```

**只有学生的 head 被更新，教师永远 `torch.no_grad()`。**

#### 代码位置

| 项 | 行号 |
|---|---|
| 教师加载（`teacher_nets[task_idx] = anchor_net`） | 1052–1074 |
| anchor term | 1371–1377 |
| ER / BC term | 1356–1369 |
| **MTD term** | **1379–1405** |
| 总 loss 组装 | 1354 / 1368 / 1376 / 1404 |

MTD 的核心 6 行（`ppo_er_unified.py:1393-1404`）：

```python
for tid in torch.unique(rp_tids).tolist():
    net = teacher_nets.get(int(tid))
    if net is None:
        continue
    sel = rp_tids == tid
    obs_sel = replay_obs_all[rp_idx[sel]]
    with torch.no_grad():
        t_mu = net(obs_sel)                      # 旧任务的专家给标签
    mtd_loss = mtd_loss + torch.nn.functional.mse_loss(
        agent.head_mean(obs_sel, int(tid)), t_mu) * (obs_sel.shape[0] / mb_size)
loss = loss + mtd_coef * mtd_loss
```

#### 教师从哪来

`--anchor-task` 传一张表，格式 `任务名=ckpt路径`，例如 `c8v2_ad.sh:26-33`：

```
"PegInsertionSide-v1=$CK/ppo_er_unified_task0_PegInsertionSide-v1_peg75m_best.pt,
 StackCube-v1=$CK/ppo_er_unified_task4_StackCube-v1_gpu5_48h.pt,
 PullCube-v1=$CK/..._c5_er_mtd_best.pt,
 ...
 PullCubeTool-v1=$CK/ppo_er_unified_task0_PullCubeTool-v1_tool30m_best.pt"
```

**关键：这些 teacher 不是 solver，是 PPO 从零预训的单任务策略权重。** 文件名里的 `peg75m` / `poke24m` / `tool30m` / `gpu5_48h` 就是训练预算（75M steps / 24M / 30M / 48 小时）。

这一点很重要，因为它说明了 MTD 的真实成本：**每个任务都要先单独 PPO 训出一个专家**，才能给 MTD 用。

### 4.4 ER 是什么（顺便说清，容易和 MTD 混）

```
replay_ratio = 0.5   →   n_replay = batch_size × 0.5
replay_buffer.sample(n_replay, exclude_task=task_idx)     # 排除当前任务
buffer_per_task = 200,000
```

**排除当前任务**是有意的：自己做自己的 replay 需要 off-policy 修正，代价高且没必要。

ER 在 loss 里以**监督项**出现（不是把 replay 数据混进 PPO 的 batch 做策略梯度）：

- 对 replay 的旧动作做 MSE → `bc_coef = 0.05`
- 对 replay 的旧观测问教师 → 这就是 MTD

所以严格讲，**ER 负责"提供旧任务的样本"，MTD 负责"用专家给这些样本打标签"**。两者是配套的：没有 replay 就没有 MTD 的输入。

### 4.5 一个容易忽略的细节：anchor 任务上 PPO 被关掉

`ppo_er_unified.py:1336-1338`：

```python
if anchor_net is not None:
    # Distillation replaces the policy gradient here.
    pg_loss = pg_loss * 0.0
```

也就是说，当某个任务配有教师时，**它的策略完全靠蒸馏学，PPO 的策略梯度项被置零**（value loss 和 entropy 还在）。

这解释了两件事：

1. 为什么 `c8v2_ad.sh` 里前 6 个任务只给 8192 步——它们不需要探索，只需要把 head 对齐到教师
2. 为什么 KL early-stop 被放宽到 `max(target_kl, 0.5)`（1415–1418 行）——蒸馏必须让策略大幅移动，标准 PPO 的 KL 闸门会把每轮更新立刻掐断

### 4.6 结果

#### 各变体终评（N=100）

| 变体 | 配置差异 | 8 任务均值 | min |
|---|---|---|---|
| `c8v2_ad` | trunk 冻结（`--trunk-lr-mult 0.0`），仅训新任务 adapter | **88.7** | 71 |
| `c8v5_cons` | 蒸馏重对齐 | **92.0** | — |
| `c8v4_picktrunk` | trunk 允许漂移 0.2 | 79.0 | — |
| `c8v7_naive` | `--seqft`，`replay_ratio=0` → **无 ER、无 MTD** | 76.6 | — |

#### c8v2_ad 的实际训练预算（`c8v2_ad.sh:24-25`）

```
SEQ   = Peg,Stack,Pull,Pick,LiftPeg,Push,Poke,Tool
STEPS = 8192,8192,8192,8192,8192,8192,4000000,4000000
```

**前 6 个任务只给 8192 步（等于不训，直接沿用 `--init-ckpt` 的权重），只有最后两个新任务训 4M 步。**

这必须说清楚：c8v2_ad 的 88.7% 是"在已训好的 6 任务模型上**增量扩展** 2 个新任务"，靠冻结 trunk 保证旧任务不退化，**不是"从随机初始化顺序学 8 个任务"**。它是合法的 CL 设定（旧任务不可重训），但它不是从零开始的 CL。

#### 一个必须承认的负结果

我们做了 3 seed 的配对对比（ER+MTD vs naive）：

| 指标 | ER + MTD | naive（无 ER/MTD） |
|---|---|---|
| 8 任务均值 | 78.8 | **80.7** |
| 配对 t 检验 | p ≈ 0.49 | — |

**ER + MTD 相对 naive 没有正贡献。** 在这批任务上，"真实旧数据回放 + 多教师蒸馏"没有跑赢"什么都不做"。

这和 §4.3 里"MTD 应该比 BC 强"的动机是矛盾的，原因有两个候选：

1. **trunk 冻结已经解决了灾难性遗忘**——旧任务的 base 和 head 一个字节都没动，ER/MTD 想保护的东西本来就没坏，自然没有提升空间
2. **单次运行方差大**（min 71 说明方差很大），3 seed 不足以区分

这一点会如实写进论文，不会包装成"MTD 有效"。

## 5. 部分四：TD-MPC2（负结果，0–7%）

### 5.1 方法

TD-MPC2 是 model-based RL：学一个隐式世界模型 + 在潜空间用 MPPI 做轨迹优化。

| 配置 | 值 |
|---|---|
| 环境 | StackCube 一个任务 |
| adapter | `maniskill3.py` |
| `model_size` | 5 |
| 训练步数 | 2M–4M |
| 规划器 | MPPI，`N`（采样数）50 或 30 |
| 实验名 | `ms3_stack_4m_ws` |

### 5.2 结果

| 配置 | 成功率 |
|---|---|
| policy-only（不规划，直接执行 actor） | **0%**（N=50 reward 10.4；N=30 reward 63.7） |
| MPPI N=50 | **0%**（reward 145.1） |
| MPPI N=30（`best_strong`） | **7%** |
| MPPI N=30（`w3resume`） | **3%** |

### 5.3 为什么失败

**warm-start 是成功的，但闭环是失败的：**

- `pi_mse`（actor 对专家动作的拟合误差）：0.887 → **0.051**（降了 94%）
- `dyn`（世界模型 loss）：0.0054 → 0.00034（降了 94%）
- 但 `mse_j120`（post-tanh 策略误差）：MSE 0.00231 / RMSE 0.0481

也就是说：**单步动作能拟合得非常好，但 120 步之后闭环就漂了。** 这是模仿学习/世界模型在长时域任务上的典型失败模式——每步误差 0.048 在 tanh 空间里经过几十步复合，足以把机器人带出可行域。

**这个负结果本身有价值**：它解释了为什么我们最终选模仿学习而不是 RL/世界模型路线。

## 7. 局限（如实列出）

### 7.1 数据集只含 `(s, a)`，不含 reward

实测键：`obs`、`act`、`ep`、`tid`（部分文件有 `task`/`succ`/`lens`）。

**没有 `reward`、没有 `next_obs`、没有 `done`。** 后果：

- ✅ 可用于：BC、DAgger、Diffusion Policy、以及 IQL/TD3+BC 的 BC 部分
- ❌ 不可直接用于：SAC/PPO/TD3（online RL）、以及需要 transition 的 offline RL

**但这不影响 EWC/MAS**：它们不用数据集，用环境 reward。8 个任务的 reward 都是 `normalized_dense`，随时可跑。

### 7.2 单头在 10 任务上失败（口径后改为 9 个稠密任务）

Pyramid 0%、Plug 0%。不是数据问题（专家 87%/89%），是**接口不匹配**：Pyramid 的上限被动作分辨率卡住，Plug 需要 IK 安全网。因此任务集收缩——先是 8 个稠密任务，后按"只保留稠密奖励"的口径改成 **9 个**（8 任务 + 关节增量版 PlaceSphere），见 §8.2。9 任务单头最优 **80.2%（8/9 ≥80%）**，唯一缺口仍是 PlaceSphere。

### 7.3 ER+MTD 没有跑赢 naive（p≈0.49）

见 4.6。这是负结果，不掩饰。

### 7.4 MTD 的成本很高

每个任务要单独 PPO 预训一个专家（Peg 75M steps、Stack 48 小时、Poke 24M、Tool 30M）。这个成本常常被"蒸馏只是加一项 loss"的说法掩盖。

### 7.5 RollBall 无解

8 版迭代仍 0%。物理约束见第 8 节。**建议放弃。**

### 8.1 PlaceSphere 是怎么从 18% 做到约 80% 的

PlaceSphere 是第 11 个任务（不在 10 任务 CL 序列内），单任务单独解决；仍是单模型、单头、
无任务标签。这里记录它的方法，因为它把"标签不 Markov 导致的天花板"这条教训量化了。

这个任务的旧数据不能用，原因不是量不够，而是**标签不 Markov**：旧专家用 screw 规划器
一次性缓出一条关节路径，再按 tick 回放，同一观测在路径不同位置对应互相矛盾的"下一步"，
BC 只能学成均值——离线拟合再好，闭环天花板也只有 ~23%（`_ft_e8` + `ASCALE=1.4`）。

三步改造（完整数据见 `CL_10TASK_RESULTS.md` §10.10）：

1. **换专家接口**：专家从"回放路径"改成纯函数 `state → 目标 TCP 位姿 + grip`，
   动作由 CLIK 每步现场求解（`compute_IK_CLIK`，`eps=1e-4`、60 次迭代、
   `dt=0.2`、`damp=1e-6`，未收敛取迭代方向；目标先乘 `robot.pose.inv()` 进 base 系）。
   这样同一个观测只有一个标签，专家 40/40 = 100%，批量采集 480 集 98.3%。
2. **DAgger 递进**：学生驱动、专家在到达状态上标注，7 轮累加到 186,336 帧 / 2,703 集
   （每轮 100 集评测：6.7% → 29.8% → 46.2% → 44.2% → 80.0% → 78.8% → 79.0% → **80.3%**，
   末项为 v12 的 7 段 × 100 集合计）。
3. **两条控制规则**（评测与采集共用同一实现，属控制器而非训练技巧）：
   目标位姿一阶滤波 `PS_TEMA=0.5`（44% → 70%），以及"搬运到位即释放"
   `PS_RELSE`（球在托盘 3.5 cm 内、高度 < 9.5 cm 时强制 `grip=+1`）。
   第二条解决的是 trace 里最典型的僵持：球已在托盘正上方 `dxy=0.000`、夹爪距球 6 mm，
   grip 却停在 −0.1 不放，一直耗到 800 步上限——因为"正在搬运"与"已经到达"在观测上同形。
   反过来试过把 grip 二值化并加滞回（`PS_GHOLD`），反而把示范里的"轻抓"丢掉了，79% → 73%，
   默认关闭。

失败不是训练不够：同观测标签仍有 2 cm 级歧义（最近邻 `|Δpos|` mean 23.3 mm、p90 44.4 mm），
v9 之后再加三轮 DAgger 只涨 0.3 个点，属于表示层面的上限。交付数字取三批合计 1,700 回合
（seed 有重叠）：7 段 × 100 集 562/700 = 80.3%，4 段 × 175 集（默认参数）553/700 = 79.0%，
打包后默认配置复核 300 回合 238/300 = 79.3%，合计 **1,353/1,700 = 79.6%**，故写"约 80%"；
单批 95% 置信区间 ±3 pt，跨 seed 段 74–86%。
两条负结果：第 8 轮 DAgger（195,778 帧 / 3,023 集 → 77.1%），新增帧多来自已成功的
短回合、分布被稀释；以及 v11 与 v12 权重 0.5 平均的 SWA（同参数量、400 回合 74.0%），
说明这类回归输出的标定是逐模型特有的，插值平均不掉误差。所以第 7 轮（`ps_ik_v12`）
就是止损点。复现：`bash _ps_ik_ev.sh ckpts/ps_ik_v12.pt 700 4 9000`（默认参数即最终配置）。

### 8.2 9 个稠密奖励任务的单头口径与 EWC 锚定（2026-11-18）

任务集从 10 个收缩为 **9 个稠密奖励任务**：Peg / Stack / Pull / Pick / LiftPeg /
Push / Poke / Tool + PlaceSphere。剔除的两项不是数据问题而是接口问题——
StackPyramid 的专家上限被动作分辨率卡住（§7.2），PlugCharger 的最佳解是
"策略接近 + IK 安全网"，两者都无法由纯 BC 单头表达。PlaceSphere 改用
**关节增量标签**（`PS_LABEL=act`），不再需要 §8.1 的"目标位姿 + CLIK 伺服"两线结构。

**两个必须先修的 bug。** `_ps_up56.py` / `_ps_dual.py` 写的是裸 state_dict，而
`_sd_train.py` 只读 `{"state_dict","norm"}`，于是 `_INIT_SD = None`、`if` 静默跳过——
v13/v14/v16/v17 实际全是随机初始化，"微调导致灾难性遗忘"的判断因此作废。另外
`SD_HIDDEN` 默认 256 与 p56 的 768 不符，会 size mismatch。两处修好后 warm start
打印 `missing=0 unexpected=0`，8 任务初始 mse 0.0016–0.0026。

**EWC 形式。** 在 8 任务帧（`tid != 10`，抽 20,000 帧）上算对角 Fisher
`I_i = E[g_i²]`，按全局均值归一化后保存 `θ*` 与 `I`；训练损失为

```
L = L_BC + λ · Σ_i I_i (θ_i − θ*_i)²
```

因为 8 任务帧里 PlaceSphere 的尾 8 维恒为零列、梯度为零，**尾维不会被锚定**，
新任务的读出层（对应的输入列）仍可自由学习。这是"仅尾维归一化 + EWC"能同时
保住旧任务、给新任务梯度的原因。

**结果**（100 回合/任务，seeds 0–99，`STACK=5`、hidden 768、lr 1e-4、120 轮、OBNOISE 0.1、PS 5×）：

| 配置 | mean | ≥80% | 备注 |
|---|---|---|---|
| `sd_single_d5_p56`（8 任务，不混训） | **93.5**（8 任务） | 8/8 | Peg 87、Stack 87、min 87 |
| v19 无 EWC | 75.4 | 6/9 | Peg 44、Stack 74 |
| **v19 λ=0.03** | **80.2** | **8/9** | Peg 77、Stack 87、Pick 95，PS 1 |
| v21 PS 10× / λ=0.01 | 79.6 | 7/9 | PS 3，Peg/Poke 被挤掉 |

EWC 净贡献：Peg **+33**、Stack **+13**、Pick **+8**，代价是 Poke −10、PlaceSphere −4。

**为什么 PlaceSphere 仍然只有 1%。** 单任务它可达 83.0%（全维归一化），并进单头后
8 任务的策略在原始尺度上（qpos ±3 rad 与 0.01 m 相对向量同层）依赖幅度区分，
而 PlaceSphere 的闭环要求 shared 48 维也标准化，否则 8 维相对向量被 proprio 淹没。
一旦标准化 shared 维，Peg 从 87 掉到 50–62。**两族对输入尺度的需求互斥**：
加份额（5×→10×，37% batch）、降锚（0.03→0.01）、加轮次（40→120）、双尺度输入
（560 维，norm 路零初始化）都无法折中。

**DAgger 复核与 v22（2026-11-19）。** 上一版这里写的"DAgger 收不到纠正，教师只有
5%"是**配置错误**造成的假结论：采集脚本 `_ps_dag_d.sh` 用 `PS_CTRL=ik`，而
`_ps_dagger.py` 默认 `screw`，复核时按默认值跑才出现 `screw plan failed` 388/800。
换回 ik 教师后，纯学生执行仍会把球推出桌面（`PS_STU=1.0` 收 0 帧），改用
**混合策略**——教师为主、学生按比例接管（`PS_STU`）——0.7 时 20 集 SR 75%、
学生执行 26%、967 帧真纠正 + 535 帧丢弃。扩到 4 worker × 50 集：

| worker | SR | 学生执行 | 丢弃帧 | 保留帧 |
|---|---|---|---|---|
| s0 | 72% | 24% | 1,037 | 2,347 |
| s1 | 84% | 24% | 700 | 2,743 |
| s2 | 84% | 21% | 509 | 2,641 |
| s3 | 70% | 23% | 1,080 | 2,126 |
| **合计** | **77.5%**（155/200） | **23%** | **3,326** | **9,857** |

v22 = v19 配方 + 这 9,857 帧（PS 帧 77,989 → 87,846，+12.6%，PS mse 0.0577 →
0.0280），9 任务评测 **79.9%（8/9 ≥80%，PS 0%）**，PS 800 步走满。

**排除"容量不足"的证据**：用 v22 作初始化、只用 PS 数据（87,846 帧）微调 8 轮，
SR 仍只有 25%，且 3/4 集 `mean|a|`=0.03–0.05（0.6–0.8 mm/步）——BC **塌缩到
"静止"这个保守解**，不是学不动。探针对照（GPU，4 集）：`ps_dl_v2` 4/4、43 步、
TCP 1.0–1.3 cm/步；`sd_9t_v22` 0/4、800 步、0.05–0.76 cm/步，3 集把球推出桌面
（z=−0.9）。注意 **mse 不能跨空间比较**：v22 的 `y_sd`=1，0.0280 是 raw mse；
`ps_dl_v2` 的 0.0298 在标准化空间（`y_sd`=0.32–0.80），折回 raw 约 0.0074，实际
误差小约 4 倍。

**结论**：8 任务 **93.5%**、PlaceSphere 单任务 **83.0%**、9 任务单头 **80.2%
（v19）/ 79.9%（v22，8/9）**。"9 个稠密任务全部 ≥80%"在严格单头、固定参数量、
无任务标签下**未达成**；教师可用（ik，77.5%）、纠正帧到手（9,857）、容量已排除，
剩下的唯一根因仍是输入尺度互斥。完整证据链见 `CL_10TASK_RESULTS.md` §11.6–11.8。

## 9. 一句话总结

> 数据集的 `(s,a)` 全部来自一个 92.0% 的 8-head PPO 模型（`c8v5_cons`），不是 solver——所以它只能喂模仿学习，这是选型代价，不是缺陷。主结论是**单头 BC + 5 轮 DAgger 在 8 个稠密任务上达到 92.4%（min 83），单模型、无任务标签**。**DAgger** 的核心是让学生自己跑、老师只负责在学生访问到的（含走偏的）状态上打标签，然后聚合重训；5 轮后学生与老师打平，也说明天花板由老师决定。CL 主实验用 PPO + ER + MTD，其中 **MTD 就是"对回放里的旧样本，按任务号找该任务的冻结专家做 MSE 蒸馏"**，把三个蒸馏项分清：anchor 管当前任务、ER/BC 管旧动作、MTD 管旧任务的专家。这条路线实测 88.7%–92.0%（multi-head 设定），但 3 seed 配对显示 ER+MTD 相对 naive 无正贡献（p≈0.49），这个负结果会如实报告。TD-MPC2 与 RollBall 两个方向的失败也已记录。另外，曾被判为"学不动"的稠密任务 PlaceSphere（旧 BC 基线 12–23%），最终靠"把专家从路径回放改成 `state → 目标位姿` 纯函数 + CLIK 伺服、让标签变成 Markov"解决，学生经 7 轮 DAgger 到 **约 80%（1,700 回合 79.6%）**，第 8 轮 DAgger 与权重平均（SWA）都是负结果。**2026-11-18 补充**：把 PlaceSphere 改成关节增量标签后单任务到 **83.0%**，拓宽 8 任务基座到 56 维零填充后为 **93.5%（8/8 ≥80%）**；但把两者并入严格单头 9 任务时，EWC 锚定能把 8 任务保在 77–100%（mean **80.2%**，8/9 ≥80%），PlaceSphere 却只有 1%——因为两族对输入尺度的需求互斥（8 任务需原始尺度、PlaceSphere 需全维标准化），加份额、降锚、加轮次、双尺度输入四类尝试全部失败。**2026-11-19 补充**：此前"DAgger
也收不到纠正"是教师配置错误（`screw` vs `ik`）造成的假结论；换成 ik 教师 + 混合策略
（`PS_STU=0.7`）后，200 集收到 **9,857 帧**学生分布纠正（教师 SR 77.5%、学生执行
23%），但 v22 仍只到 **79.9%（8/9，PS 0%）**，且同配方 PS-only 微调 8 轮也只有 25%
并塌缩到"静止"——**容量与数据量均已排除**。故"9 个稠密任务全部 ≥80%"在本约束下
未达成（§8.2、`CL_10TASK_RESULTS.md` §11）。
